# BAZARSPORT — независим деплой от GitHub (без ChatGPT Work)

**Статус:** план, неактивен деплой. Не променя живия `https://bazarsport.eu`.

## Извод

Понастоящем проектът се публикува чрез ChatGPT Sites. Файлът `.openai/hosting.json` сочи към съществуващ Sites проект и D1 binding `DB`. Това **не е** Cloudflare Wrangler конфигурация за автоматичен GitHub→Sites деплой. Стандартен GitHub Action не може да публикува сигурно към същия Sites проект само чрез този файл.

За независимост от Work ще подготвим самостоятелно хостване на приложението в **Cloudflare Workers + собствена Cloudflare D1 база**, свързано с GitHub. Cloudflare Workers Builds поддържа автоматичен деплой при push към GitHub.

Преходът се извършва **само след успешно тестово внедряване, експорт и проверка на реалните записи**, а не чрез директна смяна на DNS.

## Защо текущото приложение не може просто да се качи другаде

- `app/chatgpt-auth.ts` и `lib/owner.ts` разчитат на защитени `oai-authenticated-user-*` HTTP headers, инжектирани от Sites. Извън тази защитена среда заглавките могат да бъдат подправени, ако не изградим ново валидиране на сесия/токен. **Без замяна на автентикацията не излагайте приложението публично!**
- `db/index.ts` очаква Cloudflare D1 binding `DB`. В настоящия Vite конфиг има *placeholder* database ID, който не представлява реалната продукционна база.
- В GitHub няма живите записи/фишове от Sites. Копирането на репото **не** мигрира базата.
- Собственото MCP свързване и входът на администратора трябва да се тестват наново.

## Фази на миграцията

### 0. Настоящият публичен сайт остава непроменен
- [ ] Потвърди, че `https://bazarsport.eu` и `/admin` работят.
- [ ] Не пипай DNS и съществуващия Sites `project_id`.
- [ ] Не изпълнявай `drizzle/0000_*.sql` или `wrangler d1 migrations apply --remote` върху текущата база.

### 1. Осигури собствена Cloudflare среда
- [ ] Собствен Cloudflare акаунт с достъп до **Workers**, **D1**, домейна/DNS и GitHub интеграцията.
- [ ] Създай тестов Worker под отделен адрес `*.workers.dev`, не под `bazarsport.eu`.
- [ ] Регистрирай **отделна** тестова D1 база в акаунта. Никакъв достъп до продукционни данни в този етап.

### 2. Защитен администраторски вход
- [ ] Замени Sites-specific `oai-authenticated-user-*` механизма със собствено проверяван вход (например Cloudflare Access JWT, валидиран от приложението, или надежден OAuth/session provider).
- [ ] Защити `/admin`, `/api/drafts` и всички mutations на сървъра; не се доверявай на невалидирани headers, дори ако клиентът скрива бутоните.
- [ ] Запази защитите срещу cross-site заявки, CSRF, replay, session expiry и преглед на правомощия.
- [ ] Тествай, че подправени `oai-authenticated-user-id`/email headers не дават права.
- [ ] Осигури всички Secrets/keys **извън GitHub кода**.

### 3. Архив/миграция на данните — блокиращо условие
- [ ] Установи поддържан достъп за експортиране на цялата текуща база, включително `entries`, `audit_events` и други таблици.
- [ ] Експортирай безопасно в криптиран архив; провери брой записи и целостта им.
- [ ] Изготви план за възстановяване и провери архивите върху тестова база.
- [ ] Прехвърли към **собствената** продукционна D1 база само след документиран и проверен експорт. Ако експортът от Sites е невъзможен, **спри миграцията**, вместо да нулираш данните.
- [ ] Пазете `published`/`draft`, времена, резултати, `approvedBy`, WIN/LOSS/VOID/UNVERIFIED и история без преобразуване.

### 4. Отделен staging build + тестове
- [ ] Използвай проверено Wrangler/Cloudflare Workers конфигуриране, с валидни bindings (собствен D1 ID).
- [ ] `npm run install:ci && npm run typecheck && npm test && npm run build`.
- [ ] Тествай начална страница, мобилна PWA, CORNER HUNTER, BET STRIKE, admin, одобрение, резултати, ROI и MCP поведение.
- [ ] Тествай от браузър без автентикация: public API не издава лични данни; private API връща 401/403.
- [ ] Потвърди, че тестовата среда не използва живата продукционна база.

### 5. GitHub CI/CD и сигурно публикуване
- [ ] Свържи конкретния Cloudflare Worker с `slavov000123-cmd/bazarsport` чрез **Cloudflare Workers Builds — GitHub integration** или GitHub Actions с Cloudflare-scoped token.
- [ ] Прегледай списъка с файлове/командата за build и конфигурацията на binding-ите.
- [ ] За staging публикувай от отделен клон; за production изисквай успешни GitHub проверки, преглед и контрол на достъпа.
- [ ] Запази rollback версия и възможност за бързо връщане на DNS при нужда.
- [ ] Конфигурирай бъдещи изменения: PR → тестове/preview → merge → автоматичен деплой в собствения Cloudflare проект.

### 6. Преминаване на домейна
- [ ] След като новата инфраструктура и копието на данните са проверени, планирай кратко редакционно замразяване.
- [ ] Финално синхронизирай записи, после настрой `bazarsport.eu`/SSL към **собственото** Cloudflare приложение.
- [ ] Провери всички критични URL, PWA, администраторски действия и резултати.
- [ ] Дръж стария Sites проект непроменен като опция за връщане, докато новата среда се стабилизира.

## Какво можем да правим сега, без Work

- Да редактираме и тестваме кода в GitHub.
- Да разработим новата система за вход и тестовите конфигурации.
- Да подготвим Cloudflare staging и GitHub интеграция след изрично свързване на собствен Cloudflare акаунт.
- **Не** можем да мигрираме текущия Sites D1 автоматично, нито да гарантираме production деплой без достъп до хостинга и валидиран експорт.
